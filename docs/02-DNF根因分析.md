# DNF「本次复原步骤不完整」根因分析

> 这份文档回答一个问题：**为什么上一版明明能连、能跟着转、能出成绩，却会在最后判 DNF？**
> 结论先给：不是"随机 BUG"，而是**四类系统性缺陷**造成的。新工程把每一条都从设计上消掉了。

---

## 0. 先把 App 的判定逻辑想清楚

从三份材料（官方逆向文档、GAN-main 的 Rust 实现、上一版固件的实测记录）可以拼出奇艺 App 的工作方式：

1. **计时/结束**：App 收到 `StateChange` 帧，看偏移 91 的 `ack` 字节。
   文档原话：*"needs ACK 字段只有在状态为复原态时才为 1"*，并特别提示
   *"把 ack=1 的帧一律当作复原态处理"*（因为真机偶尔会在最后一步是中层转时
   状态没同步上，但仍用 ack=1 喊"我复原了"）。
   → **ack=1 就是"这一把结束了"的信号。**

2. **复盘**：结束后 App 要把这一把拆成 C/F/O/P 四段，还要算步数、TPS。
   这必须有**完整的动作序列**——不是只要有贴纸。

3. **"步骤不完整"的含义**：App 自己那份动作序列，**推不到它被告知的那个状态**。
   也就是：
   ```
   replay(收到的动作) != 收到的贴纸 / 复原态
   ```
   只要这个等式不成立，就弹窗。

于是问题就变成一句话：**我们发出去的"动作"和"状态"必须永远自洽，且一步都不能少。**

而上一版在这两件事上都有系统性缺陷。

---

## 1. 缺陷 A：历史区写反了（最隐蔽，最像"偶发"）

奇艺 `StateChange` 帧里有一段 55 字节的"历史区"（偏移 36..90，11 个槽，每槽
`时间戳:4 + 转动码:1`）。App 用它来**补它漏收的步**、以及给复盘的步序做校对。

**真实魔方的写法**（协议文档抓包 + GAN-main 的 Rust 编码器，两者一致）：

| 槽位 | 偏移 | 含义 |
|---|---|---|
| 10 | **86** | **最新的一步**（上一手） |
| 9 | 81 | 再上一手 |
| … | … | … |
| 0 | 36 | 最旧的一手 |
| 空槽 | — | `FF FF FF FF FF` |

文档里的抓包例子长这样（注意 `ff` 在前、真实数据在后）：

```
fe 5e 03 <ts> 33 33 33 33 ... 08 64 ff ff ff ... ff 00 03 00 c6 01 00 03 04 ee 02 00 06 94 ab 07 01 XX XX
                                          ^^^^^^ 空槽全是 FF                        ^^^^^^^^^^^^^^^^^^^^ 最新三步在这里
```

**上一版固件的写法**（`qy_proto.c` 的 `hist_push` + 历史区填充）：

```c
// 最新一步写在偏移 36（开头），越旧越往后
```

两者**正好相反**。一旦 App 用这段历史去补步或校对步序，就会把 11 步的顺序整体
倒过来 —— 表现就是"前面都对、最后突然说步骤不完整"。

> **可信度：高。** 这不是推断，是三份独立材料 + 一份抓包 hexdump 的交叉验证。
> 新工程的 `qy_codec.c` 按"最新在偏移 86"实现，并且 `selftest` 里有逐字节断言。

## 2. 缺陷 B：丢步（最致命，直接导致 DNF）

App 的动作模型是加法：**少一帧，它的模型就停在错误的状态**，最后永远回不到复原。

上一版有几条路径会真的丢帧：

### B1. 把"中层转"当坏数据跳过
交接文档 #9 原文：

> 中层转 M/E/S 导致整把 DNF —— 魔方把 M 上报成两次近乎同时的面转（L + R'，间隔 0~4ms）……
> **不再当坏数据处理：跳过不断连**

**"跳过"就是丢了一步。** 你做了一条含 M 的公式，App 少收一步，最后必然
"步骤不完整"。这也解释了为什么这个 BUG 看起来"偶发"——**只有用到中层转的那些把次才会触发**。

> 正确的做法：魔方把它拆成 L' + R，我们就把 **L' + R 两步原样发出去**。
> 这两步在奇艺的 12 码里完全合法，状态也自洽。**它就是对的，不要过滤。**

新工程的处理：
* 如果魔方报的是**两个面转** → 原样两步发出去（正常路径）。
* 如果魔方真的报了 `code ≥ 12`（M/E/S 本体）→ **停机告警**，不再静默丢帧；
  由用户按 App 的"复原重置"做一次干净的重同步。理由见 [第 5 节](#5-关于-mes-的实话)。

### B2. 通知队列丢弃/积压
上一版日志里出现过 `通知被丢弃`、`发送积压`。任何一次丢弃 = 少一步。
新工程：发送队列 **只进不出、按序重试、绝不跳帧**；队列满就明确报错并标记
"状态未知"，绝不"少发一帧当作没事发生"。

### B3. 节流/合并
"每步只发一帧""把 0~4ms 内的两步合并"这类优化，本质上都是在改动作流。
新工程：**一个物理动作 = 恰好一帧，不合并、不重排、不补发。**

## 3. 缺陷 C：中途用魔方快照覆盖本地状态

交接文档 #12：

> "虚晃一下又弹回复原"（做一步 U，App 转一下又回去）… r 版逻辑里"核对不一致就采纳魔方状态"，
> 而魔方给的是**过期快照** → 补发 CurrentState 把 App 拽回去。

这不只是"看起来闪一下"：**它让某一帧的状态和动作对不上**。
App 的动作模型被突然拽到别处，后面的复盘自然对不上。

新工程的不变量（写进代码注释和文档）：

> **本地状态只由动作流推进。**
> 魔方快照只在"状态未知"时才被采纳（连接后第一次、丢步后、重置后）。
> 已经同步的情况下，快照只用来打告警，**永远不覆盖**。

---

## 4. 缺陷 D：ack 时机

`ack=1` 是"我复原了，结束这一把"的信号。两个方向都会出问题：

* **该有时没有**：最后一步没带 ack，App 只能靠贴纸猜，容易判"不完整"。
* **不该有时有**：状态没复原却带 ack=1，App 就在错误的状态结束了这一把。

新工程：`ack = cube_is_solved(本地状态)`，**每一帧都重新算**，且本地状态与
发出去的贴纸出自同一次计算 —— 两者不可能不一致。

## 5. 关于 M/E/S 的实话

奇艺协议只有 **12 个面转码**（L L' R R' D D' U U' F F' B B'），
没有中层转。这是**数学上的限制**，不是我们没实现：

* 中层转会带走中心块，而 12 面转的 cubie 模型里中心块永远不动；
* 所以任何"M → 两个面转"的替换都会让**贴纸和动作对不上**，必然 DNF。

但实际比赛里这几乎不是问题：**实体魔方自己就把 M 拆成两个面转上报**
（交接文档实测：L + R'，间隔 0~4ms）。我们要做的只是**照抄**。

真正要避免的是：
1. 解法里主动用 M/E/S 公式（比如某些 H-perm/Z-perm 变体）——**比赛别用**；
2. 万一下层固件版本真的上报 `code≥12`，不能静默吞掉（上一版的错），
   必须停机告警 → 按 App 复原重置重来。

## 8. 追加实测（2026-11-01，真机 + 真 App）：历史区才是"一转就乱"的元凶

### 现象

第一版固件（历史区按"最新在偏移 86、空槽 0xFF"填写）在实际 App 上表现为：

* **拧一下，虚拟魔方动好几步**，非常混乱；
* **最终颜色还不对**；
* 但本地模型与实体魔方**始终一致**（`[verify] 一致`，`verify_bad = 0`）。

也就是说：我们发出去的状态是对的，但 App 自己又"多走"了。

### 定位过程

关键的一步是**把调试旋钮做成运行时可切换**，然后一次只改一个变量：

| 变量 | 结果 |
|---|---|
| 历史区填满（最新在偏移 86） | 混乱、结果错 |
| **历史区全 0xFF（不发历史）** | **立刻正常，最终颜色正确** |

### 结论

**这个 App 会把 `StateChange` 里偏移 36..90 的历史区当成"待执行的动作"来重放。**

于是：

* 我们填 11 步历史 → App 每帧多走 ≤11 步 → 混乱、结果错；
* 填 0xFF（空槽）→ App 无事可做 → 只按偏移 34 的那一步走 → 正确。

协议文档里真机抓包确实填了历史（最新在偏移 86）。真机为什么不乱，我们**还没有完全解释清楚**——
可能是方向、也可能是时间戳窗口（App 只重放"比上次同步更新"的条目）。
但在搞清楚之前，**不发历史是正确且安全的**：

* 我们每步都发一帧，App 从不缺步，不需要历史来补；
* 空历史 = 真机刚开机/刚同步时的合法状态，App 必须能正确处理。

### 现在固件的默认行为

`bridge.c` 里 `hist_mode = 0`：偏移 36..90 一律填 `0xFF`，
偏移 34 放本次转动码，偏移 91 放 ack。串口 `hist 1/2/3` 仍可现场切回去做对比实验。

> **教训**：协议文档里的字段"该填什么"和"这个 App 实际怎么用"是两件事。
> 这次是靠"现场旋钮 + 一次只改一个变量"定位的，不是靠读文档推出来的。

## 9. 一张对照表

| 失败模式 | 上一版 | 新工程 |
|---|---|---|
| 历史区方向 | 最新在 36（反了） | 最新在 86，空槽 FF（有逐字节自检） |
| 中层转拆成两步 | 当坏数据**跳过** | 原样两步发出 |
| 发送队列满 | 丢帧 | 阻塞/报错 + 标记未知，绝不丢 |
| 魔方快照与本地不一致 | 覆盖本地 → 弹回 | 只告警，不覆盖 |
| ack=1 | 依赖状态推断 | 每帧按本地状态重算 |
| 中途补发 CurrentState | 会补发 | 只在 App 请求时回 |
| 连接间隔 | 30~50ms，易积压 | 请求 15~30ms，降低积压/补放 |

## 7. 怎么在真机上验证（把结论坐实）

新固件的串口日志已经把判据都打出来了：

```
[mv 17] U'  ts=... dt=180ms              ← 每一步一帧，步号连续
[mv 18] R   ts=... dt=...    => ACK=1 (复原)   ← 只有真复原才有
[app] SyncState (复原重置/重新同步)        ← App 主动强制状态
[bridge] 快照与本地不一致(仅告警, 不覆盖)   ← 出现说明丢步，要查
[bridge] 丢步: 计数跳变 ...               ← 出现说明链路丢了包
[bridge] 收到中层转 raw=12 ...            ← 出现说明魔方直接报了 M
```

**验收判据**：
* 一整把打完，`[mv n]` 的 n 从头到尾**连续不跳号**（这就是"一步不少"的硬证据）；
* 最后一步带 `=> ACK=1`；
* 不出现"丢步"和"快照不一致"告警；
* App 不再弹"本次复原步骤不完整"。

如果仍然偶发 DNF，请把那一把的完整串口日志留下来 —— 上面每一行都能定位到
具体是"少了一步"还是"状态错了一拍"。
