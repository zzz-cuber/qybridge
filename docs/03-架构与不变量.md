# 架构与不变量

## 一句话

**把"实体魔方的动作流"逐条翻译成"奇艺 App 听得懂的动作流"，其余一概不管。**

这一版和上一版最大的区别不是代码量，而是**职责收窄**：上一版做了很多"聪明事"
（核对状态、纠正偏移、过滤异常、跳过节流），每一件都在改动作流，每一件都能
变成 DNF。新工程只做翻译。

## 数据流

```
        ┌──────────────────── 实体魔域魔方 ────────────────────┐
        │  0xA5 转动帧（5 步 + 步数计数）  0xA3 状态快照        │
        └───────────────────────┬───────────────────────────┘
                                │ BLE 通知（NimBLE host 任务）
                    ┌───────────▼────────────┐
                    │ moyu_client            │ 解密 → 解析 → 投递
                    └───────────┬────────────┘
                                │ runtime 队列（唯一写者模型）
                    ┌───────────▼────────────┐
                    │ runtime 任务           │ 串行处理事件
                    │  └─ bridge             │ 动作流 → cubie 状态 → 奇艺帧
                    └───────┬────────┬───────┘
                            │        │
        奇艺帧(明文)         │        │        命令(0xA3/0xA2/...)
                    ┌───────▼──┐  ┌──▼─────────┐
                    │ qy_server│  │ moyu_client│
                    │ 补零+AES │  │  加密写回  │
                    │ 发送队列 │  └────────────┘
                    └───────┬──┘
                            │ BLE 通知（NimBLE host 任务）
                    ┌───────▼────────────┐
                    │ 奇艺 App           │
                    └────────────────────┘
```

## 模块

| 文件 | 职责 | 依赖 |
|---|---|---|
| `cube_model.c` | cubie 状态引擎、贴纸串、奇艺 27 字节打包 | 无（纯 C） |
| `qy_codec.c` | 奇艺帧的组帧/校验/AES/解析 | `esp_aes` |
| `moyu_codec.c` | 魔域 20 字节位流解析、重置帧、加解密 | `esp_aes` |
| `bridge.c` | **核心**：动作流 → 帧；状态机；不变量 | 上面三个 |
| `runtime.c` | 唯一持有 bridge 的任务 + 事件队列 | `bridge` |
| `qy_server.c` | BLE 外设（伪造奇艺魔方）+ 发送队列 | NimBLE |
| `moyu_client.c` | BLE 主机（连实体魔方） | NimBLE |
| `selftest.c` | 上电自检（不需要手机/魔方） | 全部 |

前三个是**纯逻辑**，不含 BLE、不含 FreeRTOS，方便单独验证与替换。

## 五条不变量（改代码时不许破）

### I1. 单一真相源
本地 cubie 状态**只由动作流推进**。外部状态只在三种场合被采纳：
连接后首次快照、App 的 SyncState、丢步/中层转后主动重新同步。
**已经同步时，魔方快照只用来告警，绝不覆盖。**

### I2. 一步一帧
一个物理动作 → **恰好一帧** `StateChange`。
不合并、不重排、不节流、不补发、不"因为看着像噪声"就跳过。

### I3. 帧内自洽
每一帧的 `贴纸`、`转动码`、`ack`、`历史区` 都来自**同一次**状态计算：

```
贴纸 = facelets(状态 ∘ 本步转动)
ack  = is_solved(状态 ∘ 本步转动)
历史 = 本步之前最多 11 步（最新在偏移 86）
```

App 的 `replay(动作) == 贴纸` 因此**恒成立**，DNF 的前提不存在。

### I4. 时间戳严格递增
虚拟时钟按魔方上报的间隔前进，同时不低于真实时间；
同一毫秒内多步时强制 `+2 tick`（1.25ms）。永不回退。

### I5. 失败要响
队列溢出、步数跳变、收到 M/E/S → **告警 + 把状态标为未知 + 请求重新同步**。
宁可让用户按一次"复原重置"重来，也不静默发一个错误的帧。

## 状态机（bridge）

```
           连接实体魔方
                │
                ▼
        ┌──────────────┐   0xA3 快照    ┌───────────┐
        │   UNKNOWN    │──────────────▶│   SYNCED  │
        │ (不接受动作) │               │ (正常转译)│
        └──────▲───────┘               └─────┬─────┘
               │                             │
               │ 丢步 / M·E·S / 发送队列溢出   │
               └─────────────────────────────┘
                     （App SyncState 也回到 SYNCED）
```

`UNKNOWN` 期间**不产生任何状态帧**（发出去的必然是错的）。
恢复靠：魔方快照（自动）或 App 的 SyncState（用户按"复原重置"）。

## 关于"App 的复原重置要带动实体魔方"

用户实测要求：App 里点"复原重置"，虚拟魔方复原的**同时**要让实体魔方内核也复原。
实现（`bridge.c: bridge_on_app_sync`）：

```
收到 SyncState(solved)
   ├─ 采纳为本地状态（App 是权威）
   ├─ 回 SyncConfirm
   └─ 若此前不是复原态 且 策略=开  → 向魔方写 0xA2（48 个 3bit = 复原）
```

* 只有在"**变成**复原态"时才下发，避免 App 每次连接/解完都重置一遍魔方；
* 串口 `policy` 可随时关掉这个行为（有些场景不希望动实体魔方）；
* `0xA2` 之后魔方会回一帧带状态的 `0xA2`，正好作为新的步数基准。

## 线程与并发

| 任务 | 优先级 | 做什么 | 禁止 |
|---|---|---|---|
| NimBLE host | 高 | GATT 回调、广播、通知发送、扫描 | 阻塞、碰 bridge 状态 |
| runtime (bridge) | 6 | 解析动作、推进状态、组帧 | 直接调 BLE API |
| console | 3 | 串口命令 | — |

* host 任务只**投递事件**（队列，50ms 超时），不读改 bridge 状态 → 无锁、无竞态。
* 发送队列的消费者是 host 任务（`ble_npl_callout` 驱动的发送泵），生产者是 bridge 任务。
* **队列满 = 硬错误**：bridge 上报，状态标未知；绝不静默丢。

## 发送泵为什么这么写

96 字节帧 + 默认连接间隔（30~50ms）很容易积压，App 会"延迟补放"，
表现为"做一步却转好几下"，也会破坏步序。所以：

1. 连接后主动请求 **15~30ms** 的连接间隔；
2. 发送队列**按序、只出队成功提交的帧**，失败就下一轮重试同一帧；
3. 每 8ms 泵一次，一次最多 8 帧；
4. 断线时清空队列，避免旧会话的帧"补放"到新会话。

## 自检都测了什么（`selftest.c`）

| # | 测试 | 挡住的错误 |
|---|---|---|
| 1 | CRC16 已知向量、AES 往返 | 校验/加密写错 |
| 2 | 复原态 27 字节 vs 文档标准字节 | 色码/面序/半字节顺序 |
| 3 | 12 个转动码与文档表逐个对照 | 面序映射（U 变 F' 这类） |
| 4 | 状态帧逐字节布局 + 历史区方向 + CRC 余数 0 | 帧布局（DNF 主因之一） |
| 5 | (R U R' U')^6、T-perm²、单面四次 | 转动表 / 复合顺序（越转越乱） |
| 6 | 贴纸串 ↔ cubie 往返 | 解析器 |
| 7 | 魔域 0xA5 位流解析（含 M 识别） | 位序、步数、方向 |
| 8 | 端到端：3 步打乱 + 3 步还原 → 6 帧、ack 正确、历史正确 | 整条链路 |

上电自动跑一遍；串口输入 `test` 可以再跑一遍并打印每一项。
